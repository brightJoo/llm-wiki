# LLM Wiki 문서 분류·갱신 설계

작성일: 2026-10-04 · 버전: 2 · 상태: 분류 계약·검증·게시 전달 구현과 독립 검토 완료. 검토에서 발견한 두 문제는 실패 재현 테스트 후 수정. 최종 CI 결과는 PR #3에서 확인. 실제 생성 실행기·정기 실행·모델 의미 평가는 후속 단위.

목적은 main에 축적되는 구현을 문서화해 다음 작업에서 현재 동작과 적용 범위를 빠르게 찾는 것. 전시에서는 “홈과 랭킹에 같은 정책이 적용되는가?”, “랭킹에서만 달라지는 조건은 무엇인가?”에 근거를 갖춰 답할 수 있어야 한다. 아래 화면·정책·조건·코드 경로는 가정이며 실제 29CM·무신사 정책이나 구축 성과가 아님.

성공 기준은 공유 규칙의 중복 방지, 화면·서비스별 조건의 잘못된 공통화 방지, Topic 선택 이유의 검토 가능성, 최종 main과의 일치, 미확인 범위의 명시. API 키 없는 오픈소스 도구라는 제약은 유지. 실행기·정기 실행은 [전체 구축 설계](2026-10-04-brightjoo-llm-wiki-design.md)에서 다룸.

## 선택한 접근

| 구조 | 장점 | 한계 |
| --- | --- | --- |
| 코드 파일별 문서 | 출처 탐색이 쉬움 | 여러 파일에 걸친 규칙이 흩어지고 리팩터링에 문서 경계가 흔들림 |
| 화면별 문서에 상세 정책 포함 | 화면 단위 탐색이 쉬움 | 같은 설명이 복제되고 공통 변경의 누락 발생 |
| 화면에서 정책·모듈·기술 동작을 연결 | 재사용 지식과 화면 차이를 함께 표현 | 적용 범위와 관계 관리가 필요 |

세 번째 구조를 선택. 화면은 탐색 진입점이고, 판단 조건은 정책 문서가 소유. 모듈 계약과 기술 동작도 각각 한 곳에 기록.

## 문서의 경계

문서 한 개는 **독립적으로 답할 수 있는 질문과, 그 답이 유효한 적용 범위**를 책임진다. 코드 파일이나 PR은 근거·변경 입력으로 사용한다.

다음 세 가지를 함께 판단한다.

1. 질문: 이 문서가 답하는 업무 질문이 기존 문서와 같은가?
2. 적용 범위: 서비스·화면·모듈·클라이언트·조건이 같은가?
3. 변경 관계: 이 지식은 기존 문서의 나머지 내용과 함께 바뀌는가, 독립적으로 바뀌는가?

## 기본 문서 유형

| 유형 | 답할 질문 | 담을 내용 |
| --- | --- | --- |
| 화면 | 이 화면은 무엇으로 구성되고 어떤 규칙이 적용되는가? | 모듈 구성·순서, 데이터 흐름, 적용 정책 링크, 화면별 설정·예외 |
| 모듈 | 이 UI·응답 구성요소는 어떤 계약으로 재사용되는가? | 입력·출력, 지원 버전, 사용 화면, 연결된 정책 |
| 정책 | 특정 업무 판단은 어떤 조건과 예외에 따라 결정되는가? | 판단 조건, 적용 범위, 결과, 기본값, 예외, 코드·테스트·승인 문서 근거 |
| 기술 동작 | 해당 기능의 캐시·조회·실패 처리는 어떻게 작동하는가? | 처리 방식, 의존성, 보장 가능한 동작, 사용하는 화면·모듈 |

화면은 사람의 탐색 진입점. 공통 정책의 설명은 대표 정책 문서에 두고, 화면 문서에는 정책 링크와 해당 화면의 차이를 기록한다.

위 유형은 전시 도메인용 분류 예시. 오픈소스 엔진은 유형·적용 범위 필드·예시를 도메인별 규칙으로 주입받도록 설계하며, 전시 화면명을 코어에 고정하지 않는다.

## 폴더 예시

```text
docs/wiki/
  index.md
  log.md
  topics/
    screens/
      home.md
      ranking.md
      brand.md
    modules/
      product-card.md
    policies/
      product-visibility.md
      ranking-order.md
    mechanisms/
      display-cache.md
```

디렉터리는 탐색용. 실제 적용 관계는 문서 간 링크와 메타데이터로 표현한다. 한 정책은 여러 화면·모듈에서 참조할 수 있다.

## 화면별 예외와 분리 기준

공통 규칙에 화면별 설정값이 다른 경우 같은 정책 문서 안에서 조건별 적용을 기록. 화면 문서에는 해당 조건과 링크를 기입한다.

다음 조건이면 별도 정책 또는 하위 문서로 분리를 제안한다.

- 별도의 질문에 답하며 적용 조건·결과를 독립적으로 설명할 수 있음
- 변경 주기나 책임 주체가 달라 기존 정책과 독립적으로 바뀜
- 예외 자체가 다른 화면에서도 재사용됨
- 기존 문서를 함께 읽어야 하는 독자와 별개 독자가 생김

문서 길이는 검토 신호로 사용하며 글자 수만으로 자동 분리하지 않는다. 대표 문서의 ID·경로는 유지하고 하위 문서를 연결한다.

## 문서에 필요한 식별 정보

- 고유 Topic ID와 유형
- 이 문서가 답하는 질문
- 서비스·화면·모듈 등의 적용 범위
- 조건·예외 또는 적용 버전
- 근거 코드 경로·심볼·기준 커밋 SHA와 관련 테스트
- 적용 화면·모듈, 참조하는 정책, 관련 문서 링크
- 정책 의미를 확인하지 못한 부분

직렬화는 아래 문서 계약의 JSON 블록 사용. 경로가 바뀌어도 Topic의 식별 정보와 기존 참조를 유지한다.
Topic ID는 제목·클래스명·폴더명에서 다시 계산하지 않는다. 질문 문장을 고쳐도 책임지는 질문·범위가 같으면 같은 ID를 유지.

29CM와 무신사는 별도 서비스 값으로 식별. 근거를 확인한 규칙만 서비스 간 공통으로 표시. 같은 클래스·테이블이나 비슷한 코드만으로 정책의 동일성을 확정하지 않음.

## 변경을 문서에 배치하는 절차

1. diff와 현재 코드·테스트에서 바뀐 사실 추출: 조건, 결과, 예외, 계약, 사용처
2. 목차·Topic 식별 정보·코드 근거에서 관련 기존 문서 후보 탐색
3. 후보의 질문과 적용 범위를 대조해 기존 문서 갱신, 적용 예외 추가, 새 Topic 생성 중 선택
4. 변경의 직접 대상 문서와 연결된 적용 문서를 확인. 설명이 달라지는 문서만 갱신
5. 문서 PR에 분류 이유와 근거 첨부. 의미를 확정할 수 없으면 확인할 항목으로 제안
6. 목차, 참조 관계, 출처, 갱신 로그 검증

한 PR에 서로 다른 정책 변경이 있으면 여러 Topic에 반영. 여러 PR이 같은 정책을 바꾸면 해당 정책 문서에 누적.

## 공통 정책의 증명과 예외 소유권

공통화 전에 판단 대상·입력 조건·결과, 실제 호출 경로, 호출 전 필터와 호출 뒤 정렬·추가 필터, 서비스·버전·플래그·외부 설정의 분기를 확인한다.

같은 helper를 호출하면 helper의 규칙은 공유된다고 설명할 수 있다. 그 사실만으로 두 화면의 최종 노출 결과까지 같다고 주장할 수는 없다. 테스트가 없어도 코드로 확인한 분기는 설명하되 테스트 유무를 별도로 표시.

| 상황 | 배치 결정 |
| --- | --- |
| 같은 판단·조건·결과를 여러 화면이 공유 | 대표 정책 한 개와 화면의 참조 |
| 같은 판단의 화면별 파라미터 차이 | 대표 정책 안의 범위별 조건표 |
| 별도로 설명할 조건·결과가 있고 독립적으로 변경되거나 재사용되는 예외 | 별도 정책과 `exception_of` 관계 |
| 이름이 같지만 판단 대상이나 실행 결과가 다름 | 별도 Topic 유지, 필요한 비교 링크 추가 |
| 공통 구현은 확인했지만 사용처·설정은 불명 | 확인한 구현 범위만 기록, 적용 화면은 확인 필요 |

업무 판단 조건은 정책이 소유하고, 화면 구성·모듈 선택은 화면이 소유한다. “랭킹에서만 사용”한다는 이유로 정책의 본문을 화면에 복제하지 않는다. 정책 조건표에는 조건·결과·범위·처리 순서·근거를 담고, 확인하지 못한 우선순위를 추정하지 않는다.

## 도메인 프로필과 문서 계약

유형 이름, 범위 차원, 서비스·화면 ID와 별칭은 사람이 관리하는 `.llm-wiki/domain.json`에 선언. 엔진은 선언된 값과 관계를 검사하며 전시 용어를 하드코딩하지 않음. LLM은 새 용어를 제안할 수 있지만 프로필을 자동 변경하지 않음.

첫 버전은 JSON 프로필과 Markdown 문서를 사용. 문서 목록·코드 경로·관계 색인은 실행 시 재생성. 외부 검색 서버와 벡터 DB는 추가하지 않음.

새 분류 기능은 프로필을 지정한 저장소에서 활성화. 프로필이 없으면 기존 일반 Topic 흐름을 유지하며 유형·범위를 자동으로 추측해 새 계약을 강제하지 않음. 전시 프로필 선택은 서비스 정책의 승인이나 코드 검증을 대신하지 않음.

프로필의 최소 형태는 아래 예시. `values`는 정규화한 ID이며 `aliases`는 후보 검색에만 사용. 다른 서비스가 같은 별칭을 사용해도 정책이 같다고 판단하지 않음. 실제 29CM·무신사 적용에서는 서비스 ID를 각각 선언하고 Demo 값을 사용하지 않음.

```json
{
  "schema_version": 1,
  "id": "display-demo",
  "topic_types": ["screen", "module", "policy", "mechanism"],
  "scope_dimensions": {
    "services": {"required": true, "values": ["demo-shop"]},
    "surfaces": {"required": true, "values": ["home", "ranking", "brand"]},
    "clients": {"required": false, "values": ["web", "app"]}
  },
  "aliases": {"surfaces": {"ranking": ["랭킹", "ranking"]}},
  "relation_rules": {
    "applies_policy": {"from": ["screen", "module"], "to": ["policy"]},
    "uses_module": {"from": ["screen", "module"], "to": ["module"]},
    "exception_of": {"from": ["policy"], "to": ["policy"]},
    "depends_on": {"from": ["screen", "module", "policy", "mechanism"], "to": ["screen", "module", "policy", "mechanism"]},
    "related_to": {"from": ["screen", "module", "policy", "mechanism"], "to": ["screen", "module", "policy", "mechanism"]}
  }
}
```

`scope`는 선언된 차원을 키로 사용하며 값은 ID 배열 또는 `null`. 빈 배열은 허용하지 않음. 관계의 출발·도착 유형은 프로필 규칙으로 검사. 문서와 프로필의 미지원 schema version, 중복 ID, 모르는 값은 명시적 오류. 기존 프로필을 LLM이 임의로 확장하지 않음.

기존 Topic의 `Scope`, `Current behavior`, `Drift`, `Sources`, `Related topics` 제목을 유지하고 `Topic metadata`, `Verification`을 추가. 직렬화는 `Topic metadata` 아래 JSON 블록으로 확정해 Python 표준 라이브러리로 읽을 수 있게 함.

```json
{
  "schema_version": 1,
  "id": "display.screen.ranking",
  "type": "screen",
  "question": "랭킹 화면은 어떤 모듈과 정책으로 구성되는가?",
  "scope": {"services": ["demo-shop"], "surfaces": ["ranking"]},
  "lifecycle": "active",
  "relations": [
    {"type": "applies_policy", "target": "display.policy.product-visibility"}
  ]
}
```

필수 필드는 위 일곱 항목. 유형과 필수 범위 차원은 프로필에 선언. 범위를 확인하지 못하면 명시적 `null`로 표시하며 이를 전체 적용으로 해석하지 않음. `lifecycle`은 `active` 또는 `retired`.

| 관계 | 의미 |
| --- | --- |
| `applies_policy` | 이 화면·모듈의 동작에 해당 정책이 적용 |
| `uses_module` | 해당 모듈을 사용 |
| `exception_of` | 특정 범위에서 다른 정책에 대한 예외 |
| `depends_on` | 해당 Topic의 계약·기술 동작에 의존 |
| `related_to` | 비교·배경 탐색. 영향 전파를 뜻하지 않음 |

관계 대상 ID와 본문의 상대 링크는 같은 문서를 가리켜야 함. 역방향 관계는 색인에서 계산해 양쪽 문서에 같은 관계를 복제하지 않음. `exception_of`는 설명 관계이며 자동 상속이나 규칙 실행을 의미하지 않음.

근거 형식은 출처 줄 `- \`<source-path>\` at \`<head_sha>\``을 유지하고, 다음 들여쓴 줄에 심볼과 입증하는 동작을 설명. 실제 값은 runtime context와 Git에서 확인. 예제의 샘플 값은 실제 검증 결과가 아님.

## 근거와 최신성

- 고정된 main head는 현재 구현의 기준. 운영 배포 완료나 실제 외부 설정을 자동으로 입증하지 않음
- 테스트는 특정 조건의 기대 동작을 뒷받침. 파일 존재만으로 통과나 모든 조건의 보장을 주장하지 않음
- 승인된 Spec·LLD는 의도의 근거. 코드와 다르면 현재 구현과 의도의 차이를 함께 표시
- PR·커밋 메시지는 맥락. 코드로 확인하지 않은 동작과 승인 여부를 대신하지 않음
- 기존 Wiki는 검색 입력. 새로운 사실의 근거로 순환 인용하지 않음

각 조건·결과에 입증하는 코드 경로·심볼을 연결. 관계없는 파일의 SHA 한 줄을 붙여 본문 전체가 검증됐다고 취급하지 않음. `Verification`에는 확인한 내용·관련 테스트·미확인 운영 조건을 기록.

Topic의 SHA는 해당 문서를 확인한 snapshot. 일부 Topic의 갱신으로 전체 Wiki가 최신 코드와 일치한다고 표시하지 않음. 문서 없는 화면·코드는 아직 문서화하지 않은 범위로 명시. 비교할 승인 문서가 없으면 Drift에 비교하지 못했다고 표시.

## 일별 최종 상태와 실패 처리

본문은 마지막 cursor부터 실행 시작에 고정한 head까지의 변경을 읽고 **최종 head의 현재 동작**을 설명. 같은 규칙이 A→B→C로 바뀌었다면 현재 동작은 C. 중간 변화는 필요한 경우 변경 근거에 남김. 변경 후 원복돼 Wiki의 의미·근거가 같으면 새 정책을 만들지 않음.

검색 한도 안에서 적용 범위를 확인하지 못했으면 전 서비스 공통이라고 쓰지 않음. 좁은 범위의 확인한 동작은 문서화하고 미확인 사용처를 표시할 수 있음. 바뀐 동작 자체를 설명할 필수 코드도 읽지 못했다면 실행은 불완전으로 처리해 cursor 유지.

검증·저장 실패 시 cursor 유지 후 다음 실행에서 재시도. 의미 검토가 남은 문서는 PR의 제안 상태로 유지하며 자동으로 main에 병합하지 않음. 저장 성공과 사람의 문서 승인 여부는 별개로 기록.

## 영향 범위와 분류 설명

정책의 역방향 관계에서 적용 화면·모듈을 후보로 찾되 모두 수정하지는 않음. 링크만 있고 설명이 같으면 검토 후 생략. 적용 조건·사용 정책·계약 설명이 달라지는 문서만 갱신. 단순 `related_to`는 자동 영향 대상으로 취급하지 않음.

각 변경에는 질문·관측 변화, 기존 Topic 후보, 선택과 이유, 범위·증거, 검토했지만 생략한 문서, 미확인 조건·설계 차이를 기록. 이를 통해 문서가 늘어난 이유와 바뀌지 않은 이유를 모두 검토 가능.

분류 설명은 compiler 결과의 별도 구조화 데이터로 반환하고 엔진이 Workflow artifact와 PR 본문으로 생성. LLM의 파일 편집 권한은 기존 Wiki 경로를 유지. 엄격한 기존 `log.md` 형식에 임의 필드를 넣지 않음.

결과 계약: `schema_version`, runtime과 일치하는 `source_key`·`head_sha`, 입력을 충분히 읽었는지 나타내는 `coverage`(`complete`/`incomplete`), `decisions` 배열. 각 결정에는 `question`, `topic_id`, `action`(`update`/`create`/`unchanged`/`retire`/`propose_structure`), `candidates`, `rationale`, `scope`, `evidence`(경로·심볼·SHA), `checked_dependents`(Topic·수정/생략 이유), `unknowns` 포함. 중요한 변경의 배치 누락과 결과의 미지원 버전은 오류로 처리.

`complete`는 입력 검토의 완료 여부이며 사람이 정책 의미를 승인했다는 뜻이 아님. `incomplete`이면 게시·cursor 진행을 하지 않음. 확정할 수 없는 범위 확대·병합은 `propose_structure`로 제안하고 기존 지식의 경계를 자동으로 바꾸지 않음.

## 성장·삭제·기존 문서

새 Topic에는 독립 질문·범위·현재 근거·기존 Topic에 넣기 어려운 이유가 필요. 중복 병합·ID 변경·기존 경로 폐기는 사람이 검토하는 구조 변경으로 제안. 과거 로그에서 연결한 경로는 안내 문서로 보존.

기능 삭제는 사용처와 대체 경로까지 확인한 뒤 기존 Topic을 `retired`로 전환. 파일 하나가 사라졌다는 이유로 전체 기능이 삭제됐다고 주장하지 않음. 삭제 사실·대체 기능·확인 시점을 기록.

메타데이터 없는 기존 Topic도 검색 후보에 포함. 변경에 관련된 문서부터 전환하며 전체 문서에 새 형식을 한 번에 요구하지 않음. 미전환 문서를 사라진 문서나 공통 범위로 간주하지 않음.

## 현재 엔진과의 호환성

기존 허용 경로·symlink·링크·목차 도달성·append-only log·source key·patch 한도 검사는 유지. 다음 항목은 추가 구현 필요.

- 메타데이터 형식, ID 중복, 선언된 유형·범위 값, 관계 대상과 본문 링크의 일치, 예외 관계의 순환 검사
- 분류 설명을 compiler 결과에서 받아 검증·게시하는 계약
- 일별 `base..head` 범위 중간에서 삭제된 경로의 근거 검사

확인한 코드상 차이: `CLAUDE.md`의 Sources 예시는 SHA 줄 끝에 설명을 붙이지만 현재 `SOURCE_ENTRY_PATTERN`은 SHA로 끝나는 줄만 인식. 새 템플릿은 설명을 다음 줄에 배치해 두 계약을 맞춤. 현재 삭제 근거 검사는 head에 존재하거나 head 커밋에서 바뀐 경로만 인정하므로 일별 범위의 중간 삭제도 검증하도록 보완 필요.

구조 검사 통과는 정책 의미의 정확성까지 증명하지 않음. LLM의 자기 확신 점수로 자동 승인하지 않음. 사람이 주요 조건의 근거와 분류 설명을 문서 PR에서 검토.

## 평가 사례와 완료 기준

구조 검사와 의미 평가를 분리. 실제 비공개 회사 코드를 공개 평가 자료에 복사하지 않음. 아래 합성 사례로 경계를 확인하고 공개 가능한 실제 변경을 사람이 분류해 회귀 자료에 추가.

| 사례 | 기대 결과 | 실패 예 |
| --- | --- | --- |
| 공통 노출 조건 변경 | 대표 정책 갱신, 적용 화면 검토 | 화면마다 정책 설명 복제 |
| 랭킹 전용 조건 변경 | 랭킹 범위의 조건·예외만 갱신 | 홈에도 같은 조건 적용으로 서술 |
| 같은 helper, 다른 후처리 | 공유 구현과 최종 결과 구별 | 최종 화면 결과까지 같다고 단정 |
| 같은 명칭, 서비스별 다른 동작 | 서비스 범위 분리 | 29CM·무신사 공통 정책으로 통합 |
| 하루의 연속 변경·원복 | 최종 head 기준 설명 | 중간 동작을 현재 동작으로 서술 |
| 상품 카드 계약 변경 | 모듈과 영향 화면 갱신 | 필드마다 별도 업무 정책 생성 |
| 클래스·경로 이동 | 근거 수정, Topic 유지 | 새 Topic 생성, 이전 Topic 방치 |
| 기능 삭제 | 사용처 확인 뒤 retired | 과거 로그 링크 삭제 |
| 외부 설정 미확인 | 미확인 범위 표시 | 운영에서도 항상 같은 값이라고 단정 |
| 기존 문서 후보 있음 | 후보와 선택·생성 이유 제시 | 검색 없이 신규 문서 생성 |
| 검증·저장 실패 | cursor 유지 후 재시도 | 처리 완료로 표시 |
| 메타데이터 없는 기존 문서 | 관련 문서부터 전환 | 기존 지식 전체를 검색에서 제외 |

평가 자료에는 기대 갱신 Topic, 금지할 범위 확장, 필수 사실·근거, 허용 가능한 대안을 포함. 정답을 파일명 하나로 고정하지 않고 같은 질문·범위를 책임지는 대안은 인정.

보고할 지표는 필요한 Topic 누락, 불필요한 신규·갱신 Topic, 근거 없는 사실, 잘못된 범위 확장, 질문별 답변 가능 여부. 초기 합성 사례에서는 금지한 범위 확장과 근거 없는 사실이 없어야 함. 실제 사례 수와 평가 결과를 함께 보고하며 구현 전 품질 수치를 주장하지 않음.

설계 완료는 문서 계약·분류 절차·실패 처리·예제·평가 기준이 검토 가능한 상태. 엔진 완료는 구현·검증과 실제 실행기의 문서 PR 생성 확인 이후 별도로 판단.

[홈·랭킹 문서와 일별 변경 배치 예제](2026-10-04-llm-wiki-display-example.md)에 이 규칙이 적용된 결과를 정리.

## 인터뷰에서 설명할 핵심

질문 예: “공통 노출 로직을 바꿨을 때 어떤 문서를 수정할지 어떻게 결정했나요?”

답변의 근거는 화면·정책 관계, 적용 범위, 기존 Topic 선택 기준, 코드·테스트 증거, 예외 처리, 분류 실패 사례. 실제 적용을 확인하기 전에는 구축 성과나 해결한 경험으로 표현하지 않음.
